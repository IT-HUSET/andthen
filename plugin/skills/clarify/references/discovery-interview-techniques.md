# Discovery Interview Techniques

For discovery answers that are vague, contradictory, solution-driven, or too shallow to spec against. Follow the answer rather than racing through a checklist, and return from a tangent to the decision at hand.

### The Five Whys
Run on every request, and again whenever the user states a solution instead of the real problem. Stop at a stable business or user need; drilling past a clear problem is noise.

### Scenario Testing
Use when a requirement sounds reasonable in the abstract but may break in practice – a concrete example, day one versus day one hundred, two conditions true at once. Fastest route to edge cases, hidden actors, and missing workflow steps.

### Extremes and Boundaries
Use when scope is fuzzy or the ask is too large. The smallest version that still delivers value, what breaks at 10x, what survives if the user has only 30 seconds.

### Trade-off Forcing
Use when everything is "important." Forced scarcity – only three things ship, A done well against A and B done adequately, what you would cut to ship a month earlier – reveals true priorities faster than generic prioritization questions.

### Laddering
Use when the answer is either too specific or too vague. **Upward**: feature -> benefit -> need. **Downward**: need -> criteria -> observable behavior.

### Perspective Shift
Use when discovery is stuck in one happy-path viewpoint. Ask as a skeptical user, an admin/operator, a support engineer.
