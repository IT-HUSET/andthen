### Workflow and skills

- **Where work starts: two questions, and `plan` answers one**: "do I know what to build?" and "one story or several?" are independent. The user answers the first; `plan` answers the second before it loads either procedure (ADR-020). `clarify` writes the PRD whatever the size; `plan` takes it, the plan recording its path in `prd` – `null` only when there is none. An open design choice that binds beyond the work or is costly to reverse goes to `decide` first (ADR-025) – `clarify`'s closing command when its PRD leaves one, Preflight's recommendation when authoring surfaces one. `prd` merged into `clarify` because users picked between the two by how complete their input looked. A PRD is never mandatory – an issue that already specifies the work is its source, and a PRD for every feature would be ceremony – which is why `prd` stays nullable rather than gaining a URL form `sourceRefs` already carry.
- **`clarify` writes the brief too, and has no unattended form**: `--brief` stops the interview at `intent.md`, the intake shape the next run folds into the PRD, on any subject. `intent.md` was dropped at the `prd` merge because 0.x users picked between two skills by how complete the input looked; a flag on one skill is a stated choice. No unattended form: the interview is the skill's value, and a pipeline that has requirements starts at `plan`. Reopens if an unattended pipeline needs a PRD `plan` cannot give it.
- **Specs are co-produced with the story breakdown**: `plan` cuts the stories and authors their FIS in one run – specs decay when divorced from the story context that motivated them, and one cross-cutting review catches inter-story inconsistencies before execution.
- **One authoring subagent per story**: `plan` on several stories spawns one fresh authoring subagent per story, never one author for several siblings, and a re-author stays scoped to its story. The one-to-one mapping keeps an `OVERSIZE:` or `PHANTOM_SCOPE` finding attributable to the story that caused it, and each retry separate. Batching siblings to amortize the shared preamble was rejected: the benchmark behind that claim was never committed, and its accounting is not comparable. Reopens if a comparable benchmark shows preamble cost dominating.
- **One no-spec change skill**: `implement-fix` takes a review report or a request, and a request is its own findings list, every item routed `Fix` by the user – so in either form the agent never invents scope, and what the request leaves unstated is reported, not edited, unless it is a Boy Scout tidy. It is `remediate-findings` renamed with that one input form; `quick-implement` retired into it rather than the reverse, because the Intent anchor, routing gate, and findings re-check were most of the remediation body and the inline form fit in about ten lines, while grafting remediation onto `quick-implement` as a mode would have inherited free text's "implement until requirements are met" as the default scope posture. Accepted: a one-line fix runs the full phases. Reopens if the inline form accretes a second body, or running the phases for a one-line fix costs more than it catches.
- **No model-only or user-only skills**: a capability is a skill a user invokes by name and a subagent invokes with arguments. `user-invocable: false` is no home for procedures, and neither is a reference to "read X and perform it" – references are rubrics, few and one level deep, except a skill's own conditional branch behind a load site its body names (ADR-020: `plan`'s one-story and breakdown references, `exec-plan`'s story and plan-run references). `disable-model-invocation` blocks Skill-tool invocation, and `now-what` routes to `exec-plan`. Reopens if a skill-invocable third tier ships.
- **Positioning terms**: AndThen is "lightweight agentic software engineering for AI coding agents" – the whole engineering job, requirements to debugging, done through AI coding agents – with spec-driven development as its main workflow, never the whole product (`8a5dd64`). "AI coding agents" names the tools, never the product.

### Authoring

- **The PRD carries its outcomes as body sections**: `Problem Definition > Target Users` and `Desired Outcome`, and `## Success Metrics` with baseline, target, and how observed. The Executive Summary derives from them, never the reverse, and validation rejects a metric that names a shipped capability. A FIS's Intent and Expected Outcomes cite these rows.
- **PRD acceptance criteria are EARS rules, FIS scenarios their examples** (2026-10-18): each FR states its criteria as `While <precondition>, when <trigger>, the <system name> shall <response>` and its unwanted conditions as `If <condition>, then the <system name> shall <response>`, replacing the separate Validation and Error Handling lists. The FIS self-review checks that every source acceptance criterion has a scenario, and those lists were not criteria, so nothing carried an error case into one. The gain in caught error and state cases is inferred, not measured. User-story criteria stay prose, because the outcome lens reads them. Reopens on recorded plan runs whose scenarios still miss the PRD's `If` rules.
- **Preflight closes, never holds**: Preflight, the closing step of `plan` – once per bundle when there are several stories – asks each open item once, recommendation first and preselected, with no defer option; in an unattended run, or once the run stopped on the item and nobody answered, the recommendation is taken as an `ASSUMPTION:` where it bites. Authoring adds no status of its own – every story it closes stays `pending` with its FIS, and what an assumption leaves unclear is the executor's to settle by best reading – so there is no `Closure:` verdict, hold, or reviewer re-entry per answer. `exec-plan`'s pre-run checks are *admission*; the preflight name stays with the interview 0.x users know. Reopens on a run where an executed unattended assumption shipped behaviour the plan-level review did not catch.
- **The model judges which forks need the user**: skills and references say where asking happens and how a question is shaped, never which discretionary forks to ask – no per-case asking rules, no lists of forks that always need a question. A fork a skill's own contract owns is asked by rule, such as `plan`'s uncovered screens and its slice-or-keep question, or whether `exec-plan` and `ship` start a feature branch before committing on the remote's default branch. On 2026-09-24 three rounds of such rules moved the `plan` eval to 1 of 5; a fixture with one fork that has no defensible default passed on the first two runs with no skill change, and the third failed only on a rubric that contradicted the skill. An eval that tests asking needs a fork like that, and its rubric requires that fork, never a question a capable model can default. Reopens on a run where a fork with no defensible default shipped as an assumption.
- **Scope trades are a self-review Note and a preflight question, not a skill**: the FIS self-review names, per component the floor option would not carry, the requirement clause buying it, the narrower reading that drops it, and what the Target User loses; Preflight puts those Notes to the user once per bundle, and an accepted trade amends the PRD through `clarify`. Never blocking – the design meets the requirements as written. The reviewer is the only agent holding both the design and the whole PRD, so a separate skill would only add surface. Reopens if trade Notes go unanswered in practice.
- **Document review is an authoring gate, not a `review` lens**: `clarify` and `plan` each run a fresh reviewer subagent on the `self-review.md` rubric, kept out of the author-loaded `fis-authoring-guidelines.md` so the author never reads the rubric it is judged by. There is no `--mode doc`: invoking `review` loaded roughly 9,000–12,000 instruction words to apply a few mechanical edits, and its matrix, report, and routing had no reader on those paths. Routing is a `blocks:` attribute on each Note, bundle coverage a per-FIS roster the breakdown's gate checks; `review` keeps only lenses with an implementation target. Reopens if a hand-written PRD or FIS needs a standalone review that `clarify` amendment or a `plan` rerun cannot give, or a several-story `plan` eval shows the roster missing a FIS-local defect.
- **`plan` has no re-entry handling**: it authors from a source and never reads an existing FIS or `plan.json` as state – no revise-in-place, live-work guard, or regeneration that keeps story state. Revising a spec or re-planning is a prompt the user writes, with finishing or resetting a started story first; a Cookbook recipe says what to write. Edge-case handling a user can prompt around is bloat that costs every run focus. Supersedes "Unstarted specs are re-authorable" (2026-09-29, maintainer ruling).
- **A FIS carries only what the executor would miss**: the reason is signal and drift, not execution cost – reading a 6,000-word FIS is 2–5% of an `exec-plan` run, whose cost is turns × context. A fact restated from a cited source, a project document, or a scenario is a second copy that drifts; **Need-to-know** and by-reference `Verify` coverage are authoring rules, not a reviewer cut duty. Past ~6,000 words with the task count in range, `plan` compresses under **Single source of truth** before `OVERSIZE:` fires. Technical Overview lives in Architecture Decision as `Flow`, under its own ~10-line cap. Tried and dropped: a reviewer cut duty, a contradiction class in the self-review, lifting the Architecture Decision line cap (the section doubled). Reopens if an executor starts handing FIS excerpts to workers.
- **Over-engineered work is discarded, and the PRD is cut first**: the first evals harness (16k lines, never ran) was redone small rather than pruned – a PRD prescribing release-grade guarantees regenerates the same bloat. Before executing a PRD or plan, weigh its FR count and acceptance volume against the problem; prefer data-only extension points, one generic code path, and "running it is the test" over meta-tests.
- **Rejected concepts are Product non-goals, not a registry**: `clarify` and `tracker triage` append a firmly rejected concept to the `Product` document's Non-Goals as one dated bullet and check that section before re-proposing one. Reopens if a project needs per-request provenance a bullet cannot carry.

### Execution

- **`--auto` is the only unattended trigger**: the flag turns the mode on, and nothing else does – not a task header, a workflow step, or a host with approvals off, because a host that cannot prompt still leaves the caller free to read the reply. An unattended run passes `--auto` to every nested skill invocation that accepts it. A 2026-09-25 change removed the flag and named the caller sentence `This run is unattended: no one can answer until it ends.` instead; its own acceptance gate reverted it two days later – the `plan` and `architecture` eval cases failed with the sentence in place of the flag. It cost more surface than the flag it replaced – a definition, two disambiguating sentences, a load line in ten skills, and a test pinning them – while hosts still inferred the mode from context, and the load line made attended `implement-fix` read the unattended rules and stop on a trivial question. A project-rules "never ask" line is no substitute either: attended sessions read the same file. Reopens if a caller needs the mode without control of the argument line.
- **No skill settles questions its own text asks**: `--auto` is the only thing that reduces a run's asks, and nothing about a skill's kind is. `unattended-runs.md` carried a § Headless-First naming four skills – `spec`, `exec-spec`, `triage`, `simplify-code` – that answered routine questions themselves even in an attended run. That set was the set which had linked the retired `automation-mode.md`: a packaging fact about where the `--auto` rules lived, read as a statement about who should ask. It contradicted `spec`'s two ask points and `triage`'s "asked once, recommendation first", and the other two carry no ask contract for it to override. On the `plan` eval it cost the ask it was meant to preserve – attended, no flag: Codex settled the PRD's self-contradiction itself in 3 of 3 runs, Claude in 2 of 3. The phrase is retired and `tests/test_unattended_runs_load.py` keeps it out; a shared reference that reads on a skill's class instead of its arguments is the shape it names. Reopens if an executor is measured stopping on a question its own text does not ask.
- **A question goes where the run stops for it**: a skill uses the host's structured question tool wherever that tool holds the turn for the answer, over consecutive calls when a round outgrows one call, and otherwise asks in the reply, which ends on the question. Codex's `plan` run asked all four contested items through `request_user_input_async`, a channel that does not end the turn, slept 50s, got `{"accepted":true}` with no answers, and finished on a report – so the reply a caller reads showed a settled plan, and the four unanswered items shipped as specified behaviour. The old test was suitability ("where it fits", "suited to the question"), which a multi-choice tool with a preselected recommendation passes perfectly; turn-holding is the property that matters, and it is host-agnostic. Turn-holding is not sufficient, because it is a property of the host's tool and the model judges it wrong – Codex reached for the non-blocking channel in 15 of 15 cells – so the duty is now stated about the run's own output ("the asking turn ends on the question, never on a report of what was produced") and binds whichever channel carried the ask. That is a clarity edit, not a fix: measured 0 of 6 on Codex, where `<collaboration_mode>` licenses continuing whatever our text says – a host limitation, not a wording defect, so a Codex failure on `plan-asks` is recorded as such and there is no third wording attempt. The five ask sites disagreed before this – `tracker` and `architecture` required an answer before proceeding, `clarify`, `preflight.md` and `plugin/README.md` did not – and `tests/test_unattended_runs_load.py` now pins every site that routes an ask to a structured tool (five at 2026-09-28). "Only where" restricted the tool without preferring it: on 2026-10-04 a Claude Code `plan` Preflight bound to "one sitting" put twelve items in the reply, past `AskUserQuestion`'s four per call, so every site now prefers the tool and every batching site splits a round over consecutive calls. Separately and not fixable here: DartClaw's Codex adapter accepts that call and neither delivers an answer nor surfaces the request, so on that host the channel is a dead end. Reopens if a host offers a non-blocking channel that does reliably deliver.
- **An assumption is reachable only from a question**: an `ASSUMPTION:` line records a choice the run made because no answer was coming – an unattended run, a subagent with no user, a question the run stopped on and nobody answered, or a reading its brief leaves to it – never an answer to a question its text says to ask and the run did not stop on. The old wording keyed it on a question "nobody answered", which the run certifies about itself: Codex closed the `plan` case with "Unanswered choices … are recorded as assumptions in the specs", having asked nothing. Asked-then-unanswered is a fact about the transcript, so it can be checked – but only if "asked" means the run stopped for the answer: a question sent down a channel the run continued past satisfied the weaker reading, which is how six Codex cells wrote their own choice into the specs. The canonical rule in `unattended-runs.md` already said "one it continued past was not asked, however the question was sent", and that file loads only under `--auto`, so attended runs read `preflight.md`'s weaker restatement; the two are now one clause pinned in both files. `preflight.md` gates its fallback the same way and has the asking reply answer nothing – no default listed, no assumption written – since a question behind its own recorded answer reads as settled.
- **A decision never stops a run**: a decision is asked once, recommendation first, or in an unattended run – one invoked with `--auto` – taken as an `ASSUMPTION:` where it bites. Only an unusable call stops – input absent or invalid, missing credentials or tooling, a dirty tree the run does not own and its skill gives no rule for, a call whose purpose is an action without consent – and in an unattended run that stop is `BLOCKED: <what is needed>`, defined once in `unattended-runs.md`; a run that tried and failed ends on its failure evidence. No `CONFUSION:`, `MISSING REQUIREMENT:`, `NO-OP:`, or per-skill trigger lists: nothing parsed them – DartClaw reads its own step-outcome envelope. The `blocked` story status is gone from the schema enum; a run reads an older plan's `blocked` row as `pending`. Reopens if an orchestrator needs a stop reason beyond `BLOCKED:` versus failure.
- **`exec-plan` never stops on FIS detail**: the FIS is the executable brief, and authoring polices its detail. A broken anchor, a missing or form-less proof, an unbound scenario, or text a `sharedDecision` contradicts is filled with the best reading and recorded under Implementation Observations; only a contradiction with no defensible implementation stops a run. Orchestration stops – unresolvable provenance, unfinished dependencies, an unsafe action – stay. A foreign change overlapping the story's hunks is left uncommitted and reported: only the commit has to stay separate, never the work.
- **No edge-case knobs, no strictness blocks, one verification run**: the code root is the git root the skill runs in; a missing reviewer subagent falls back and says so in `Reviewed:` rather than blocking; a story runs one tier, not fast then full. A knob for a case the maintainer handles by hand costs a flag, a validity rule, a trigger, docs, and tests. Reopens on a case a frontier model running in the repo cannot handle without it.
- **A plan run hands off the plan-level review**: `exec-plan` on a plan directory gates the run on the full tier, iterated to green like any objective gate, and the report ends on a `Next (fresh session):` line (`review --fix <plan.json>`) instead of an in-session review loop – after N stories the run session is the most loaded context in the workflow, and `implement-fix` already owns review → fix → closure, including findings the per-story review left open. Reopens on evidence that a fresh-session review misses cross-story defects the run session caught.
- **A plan runs story by story by default**: `plan`'s `Next (fresh session):` line names the first dependency-ready story's FIS, and each story run names the next, so a person reads every result and can adjust the stories ahead before they run (2026-10-17). A story run carries each discovery that affects an unstarted story into that FIS before its commit, as a plan run does between stories, and commits it, because the next run treats an uncommitted edit to its own FIS as foreign. The plan directory stays the route for unattended and parallel execution; story by story pays one full tier per story where a plan run pays one on the final tree. `plan --auto` prints the first story too, since `--auto` makes the authoring run unattended, not the execution, and a runner that chains `Next` lines still finishes the plan. The pause is where a person adjusts the spec ahead (2026-10-19): a discovery that contradicts an unstarted FIS, or changes scope, is asked before the row is written, and a yes makes the `Next` line that revision, `plan` with the discovery in its request since `plan` has no re-entry handling, or `clarify`'s amendment. The next story attests each inherited Discovered Requirement over its proof, so its reviewer checks it. Reopens on evidence that the pause between stories catches nothing a plan run's discovery triage would not.
- **Each story is simplified before the next builds on it** (2026-10-18; once per plan since rc.4): `exec-plan` dispatches `simplify-code` over a `done` story's code as its own `refactor` commit – a story run after its commit, a plan run after each story or once per `--worktree` batch – so the next story and the person reading between stories meet tidied code, since an agent adds code but never volunteers repair. The premise changed, not the evidence: the once-per-plan pass assumed no reader between stories, which the story-by-story default ended. Its cost argument stands, one pass per story. Its duplication argument holds only for parallel siblings, which the batch pass sees merged, because a sequential pass sees every earlier story in the tree. Not in `implement-fix`: its patch is the smallest the finding needs, and its trace test edits back any hunk no finding maps. Reopens on shipped duplication where an earlier story's code repeats a helper a later story added: that story's pass may not edit the earlier code, so only the reader and the plan-level review catch it.
- **The `Product` document is read where scope is chosen or the result validated, never where code is transformed**: `simplify-code` and `implement-fix` on a report anchor on the governing FIS or PRD, because `plan` already distilled what binds and a behavior-preserving or finding-bounded change cannot choose scope; the review after it catches an accidental breach. `implement-fix` on an inline request adds the Non-Goals, since no spec distilled them. Reopens on a run where a transforming step shipped a change the `Product` document forbids.
- **A fresh-session hand-off says so in the line it prints**: every pipeline skill closes on one `Next (fresh session): <command>` line, the command in the host's invocation syntax, taking the first case of its Follow-up that applies. The Architecture document's Conversation Boundaries map is for maintainers. The user sees only the printed line, and a bare command reads as "continue here": 0.x carried clean-session tips, 1.0 trims dropped them, and a 2026-09-24 manual `plan` run closed on a bare `exec-plan` command. The two words are the contract, not trimmable prose. One shape, because a 2026-10-02 audit found two: `clarify` and `plan` printed prose that does not paste. It also found menus in `ui-ux-design` and `review`, and `decide` and design reachable only by an aside. Reopens if a host starts skill hand-offs in a fresh context on its own.
- **Per-story parallelism is plain git in the run session, not AndThen scripts**: `exec-plan --worktree` on a plan directory gives each story of a batch of the wave its own worktree – `git worktree add`, then a `--no-ff` merge per return – as prose the run session executes. Each story carries its code, FIS appends, and its own `plan.json` row, edited in place so sibling rows merge cleanly and nothing is reconciled; a conflict of lines both sides appended to the changelog or `Learnings` keeps both, and any other fails that story with the conflicting paths, worktree and branch preserved. No `--team`, `--max-parallel`, or `merge-resolve` squash protocol: Agent Teams is host-experimental, and squash was what made rollback, the `Squashed-story:` trailer, and `branch -D` necessary.
- **The `ops` skill and its script are retired**: the session executing a story edits its `plan.json` row with its file tools, and a `plan` breakdown's story subagents never write the plan (ADR-003) – which closes the 0.14.4 concurrent-writer collision (`e5202ed`) without reconciliation code, since no copy of the file has two writers at once. A story run of `exec-plan` (direct on a FIS, or a plan run's story subagent) loads neither `plan-schema.md` nor `plan.schema.json` and writes its row from `story.md` alone – `status: in-progress` before its first edit, then at Step 4 `fis`, `completedTaskIds`, `verified: {at, summary}`, and `status: done` – and under `--worktree` the row is edited in place (2026-09-29): a review found no silent rule whose absence yields a row that fails validation or is misread (serialisation layout is valid either way, only two hand-started direct runs in one tree could race), and each story run loads about 620 fewer words. Reopens if a story-written row fails validation or is misread on a recorded run. No script parses an agent-read document – FIS, Index, Key Dev Commands, Learnings – for meaning: each parser pinned its document's shape (the Index could not stop being a table, a FIS bullet could not gain a word before its id), and that cost was paid on every edit of the document. No validator for plans or models: none caught anything on a recorded run, a dangling FIS pointer surfaces when the FIS is opened, and producers check their candidate against the schema shipped beside its reference. Accepted: a malformed plan or model can be written. Reopens on a run where a hand-written row breaks execution or a consumer refuses a model.
- **`exec-plan` carries minimal resume text**: a re-run relies on the plan fields and the standard workflow. Only lines whose absence is destructive or silent stay: a re-run's own edits are not foreign; a failed worktree story keeps its branch and worktree, and a rerun resumes on them; a resumed `story/{id}` may be a descendant of the base; under `--worktree` the review and fix run in the preserved worktree (2026-09-29). Reopens on a recorded re-run that loses or duplicates work.
- **Unattended remediation dispositions Notes on its own recommendation; attended remediation asks before any Tech Debt write**: the reviewer's `Fix` bar is unchanged, but an unattended run has nobody to answer the list an interactive `implement-fix` returns, and 1.0 runs left `Note` and `NOTICED BUT NOT TOUCHING` items piling up unread. An unattended `implement-fix` applies a Note it would change unasked – inside the reviewed surface, within Intent, one provable remedy, no open decision settled – defers the rest to the Tech Debt Backlog with the recommended remedy, or closes it with a reason; `--auto` is the approval for those backlog writes. An attended run writes no backlog entry on its own: it lists every `DEFERRED` finding with its blocker and remedy and writes only the ones the user approves, because the backlog should not grow without a human choosing it (2026-09-29). `review` reads a story's recorded open items as it reads earlier reports. Reopens if an eval shows it applying marginal observations.
- **A change tidies what it finds**: a story, an `implement-fix` round, a triage fix, and a prove-it refactor step make every Boy Scout tidy they find – a behavior-preserving fix in a function or doc section the change edits or a minor mechanical or check-covered one elsewhere, or an obvious small bug in an edited function fixed under a test – and name them; `NOTICED BUT NOT TOUCHING` is kept for what no tidy can fix and someone should act on. The 0.15.1 default of surface-don't-fix sent a smell the implementer could fix in one edit through three passes: recorded in the FIS, read back by the review as a finding (a "did not touch" note inside the change is a MEDIUM finding by `review-calibration.md` rule 7), then applied by the fix round. Rule 7's radius matches the tidy's. A redesign, a public API change, or a change that settles an open decision or reverses a recorded one is never a tidy (2026-10-03). Widened from the files the change touches (2026-10-15), because reports still filled with minor issues a behavior-preserving edit could clear; a parallel `exec-plan` story keeps its tidies to its own files and lists the rest, since a tidy elsewhere can conflict with a sibling at merge. Reopens if a review or eval shows a tidy hiding a regression.
- **Test-first is a project convention, not a flag; Prove-It is mandatory**: the `Testing Strategy` document's test-first answer turns it on, since a document survives a fresh story session and a per-run flag does not; a request can ask for it too. Where it applies, each test's red failure is quoted. `testing --mode tdd`, `tdd-discipline.md` and `exec-plan --tdd` retired (2026-10-20): Böckeler, "TDD inside the agent loop – theater or actual value?" (martinfowler.com, 10 Aug 2026) measured 3–8.5× tokens and no measured gain, and the procedure restated canon the model knows. Prove-It rests on its own rationale, proof the bug existed and the retained regression guard, which those studies do not measure. `implement-fix` keeps test-first because, with no FIS, writing order is its only independence check. Reopens on a measured gain from a TDD prompt that carries a test list.

### Review

- **Outcome validation is a `review` lens, not a skill**: `outcome` validates the finished feature against its PRD's Problem, Target Users, User Stories, and Success Metrics, walked as those users, and runs in `mixed` and the plan-level chain. Every mechanism it needs is `review`'s; it is not a gap dimension because gap's `## Verdict` block is frozen for comparability, and conformance and validation are different verdicts. A PRD-side finding (`spec-stale`, `ambiguous-intent`) counts toward readiness only at CRITICAL or HIGH: `clarify` and `plan`'s Preflight settle PRD decisions before execution, so a lesser one is a PRD decision for the user that no fix round makes, and counting it held issue #3's loop at Needs Fixes (2026-10-15). A one-story `plan` amends the PRD with its requirement-level answers too, so the lens does not raise them again. Reopens if post-release measurement becomes an AndThen concern.
- **A PR is reviewed as a local tree, not through the API**: `review` takes `PR <n>` or a URL as the target. `git fetch refs/pull/<n>/head` plus a detached `git worktree add` with the hooks path and LFS smudge disabled executes nothing (verified on git 2.53), and the tree gives every lens its normal read and every tool a path. The safety boundary is execution, not fetch: the project's checks run when the head branch lives in the repository, since pushing there took write access; a fork PR (`isCrossRepository`) gets a static pass unless the user says otherwise. The worktree follows the host (`.claude/worktrees/` on Claude Code), else the session temp directory; a `CLAUDE.md` in it can reach Claude Code's context, accepted under the evidence-not-instructions rule.
- **A review reads earlier reports as input, and a remediated one narrows scope**: it states each earlier finding resolved, still open, or regressed and names the latest in `**Follows**:`. When that report carries `**Remediated**:`, the follow-up reviews `git diff <its Revision>`, the callers of the code it changes, and the report's open findings; the fan-out and `security` triggers read that delta, and no reviewer count or shared-contract rule decides when to widen. rc.4 cut follow-up narrowing and every follow-up became a full run, which in trellis cost four to six reviewers per round, about 70% of the slice's review spend; the round that found a late HIGH was a `--quick --fix` over `git diff d805add`, so a delta still finds real defects. The loop ends because only fixes ask for another round: a fixed CRITICAL or HIGH finding or a partly fixed one, never an UNRESOLVED one the next round fails the same way. A `plan.json` remedy routes `Note`, since no fix round may write the file, and a MEDIUM or LOW finding surfaced or deferred stays in the summary's list instead of returning as a finding. Issue #3's fourth round was held open by exactly those (2026-10-15). Reopens if a delta follow-up misses a defect a fix introduced outside the changed code and its callers.

### Project documents

- **Durable documents carry no size ceilings**: Index entries are name and location, then the read/update trigger – no size number: a count cannot tell necessary explanation from dispensable text, which is why the ceilings, their `hard` form, `prune`, and the admission regexes all retired. Documents are read whole and so stay short. An entry's trigger may name the part to read only for history or user-facing reference that pruning would damage, never for a document a task is checked against, where a partial read misses silently. One that outgrows that becomes an index over topic files beside it, one pointer line each, a shard opened when the task names its topic – by hand, with no verb or size check. The numbers that are load-bearing live where they are used: the FIS oversize threshold in `plan` and the authoring guidelines, the 200-character glossary row rule in the Ubiquitous Language header. Reopens on a document-growth failure the read-whole convention did not prevent, or a part read that missed what the task needed.
- **The Index entry catalog carries no Product Backlog or Changelog entry**: each entry is the location its first writer creates the document at (ADR-022), so an entry no skill writes or reads is dead weight. No skill reads a backlog – a deferral stays in its PRD's `Scope > Out of Scope`, a put-off fix in Tech Debt – and a changelog would need a completion clause in `exec-plan` and `implement-fix`, not an Index entry. A project that keeps either adds its own entry.
- **No `Stack` document**: every row of its template projected the manifest, the lockfile, an ADR, or the Architecture document's Integration Points, and adopting projects showed versions drifting from the lockfile within weeks. The baseline (language, runtime, main framework) is one sentence in the Architecture document's System Overview, a library choice with a reason is a Decisions row, a rejected one a Product non-goal, and versions stay in the manifest. Reopens if a polyglot repository with no single manifest needs an inventory the Architecture document cannot carry.
- **Tracker setup is first-use, not an `init` gate**: `init` writes neither the file nor its Index entry; the first skill that needs the backend – a reader handed a non-GitHub URL, `tracker triage` with no remote, `tracker publish` at first publish – offers `tracker setup`, and an unattended run blocks naming the `Backend:` line to set. `Backend: none` declares that the project has no tracker: `tracker publish` and `tracker triage` end on one line saying so, naming the line to change, and run no `gh` flow. Accepted: a non-GitHub project's first unattended run blocks until the document exists. Reopens if a project needs the backend declared before any skill sees a URL.
- **`init` wires the rules and role agents in prose, not a script**: both are one-line offers in its closing summary (ADR-022), and a taken-up offer runs the prose in `init/references/offers.md`. `wire.py` was 328 lines plus 388 test lines for work the prose does in 18, re-deriving what the agent already has in context. Reopens if an unattended `init` needs a machine-checkable wiring result.
- **The architecture-model schema is for code-structure graphs only**: `ref` anchors to repo-relative paths and `evidence` makes every edge refutable against code, so it never adds another `kind`. Any other record follows ADR-029's rule: a JSON model, with its own schema, only for facts a skill generates and nobody hand-edits that no document holds, and never a mirror of a document.

### Packaging and measurement

- **AndThen owns the artifact contracts; downstream tooling owns its views**: the artifact schemas, the `scripts/fixtures/renders/` corpus with its owner routing, and the visual-review-notes payload are AndThen's. A downstream viewer's boards, atlas, and notes loop are its own, and it closes that loop by invoking the owning skill directly; no shipped skill reads the payload. AndThen's one view is `visualize`, a model-written page checked by rendering it (ADR-027). Shipped skills never name a downstream app – "downstream tooling" at most – because a prompt naming a private tool breaks for everyone without it.
- **No tests inside the plugin directory**: every suite lives in `tests/`, because both hosts install `plugin/` wholesale with no exclude list – a test beside a shipped script ships to every user. Reopens only if a host gains an install-time exclude.
- **Codex does not substitute `${CLAUDE_PLUGIN_ROOT}` or `${CLAUDE_SKILL_DIR}` in skill text**: its shim is a hook environment variable only. References are therefore skill-root-relative, since both hosts announce that root: `../../references/<name>.md` for a canonical, `<skill-dir>/scripts/<name>` for a bundled script, no tokens anywhere (`--validate-only` rejects them). Reopens if the Agent Skills spec standardizes a path variable; upstream `openai/codex#35702` asks for Claude-compatible aliases.
- **Leanness is measured per consuming path, and dedup never creates a reference file**: the number is the active lines a use case loads – body plus every reference it names – not SKILL.md size; a pointer pulls the whole file into every consuming bundle, so one 40-word sentence copied into five skills costs less than five links to an 850-word canonical. Report per-path loaded lines before and after; minor duplication with canonical wording is the accepted shape.
- **No context-budget gate**: shipped-prompt size is bounded by `install-skills.sh --validate-only` and the shipped-surface word budget; the ratchet cost a fixtures directory, a ceilings file, and wording gotchas without producing a finding after its baseline.

### Evals

- **Eval cells run the plugin, not the operator**: a snapshot of the working tree's `plugin/`, the role agents `init` bundles (committed as project agents), and nothing else of `~/.claude` – no user `CLAUDE.md`, output style, or MCP servers, and a run staged outside the repo so its `CLAUDE.md` does not load either. The operator's rules made a cell measure them instead of the plugin (2026-09-24 `plan` cells); the roles stay because subjects without a `reviewer` ran critics as general-purpose at high effort. Codex keeps only what DartClaw's pinned state dir forces. A case with a fuzzy criterion is fixed or cut, never kept.
- **`claude plugin eval` is not the eval harness**: Claude-only, no code graders, long journeys cannot run in it, and a skill-trigger suite is rejected outright. Wanted instead: baseline cells inside the DartClaw harness measuring core journeys against no plugin. Reopens if plugin eval gains code graders or a second host.
